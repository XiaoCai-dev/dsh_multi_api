**Многоканальный ретранслятор моделей для [DeepSeek Harness](https://github.com/deepseek-ai): одна логическая модель на нескольких OpenAI-совместимых эндпоинтах, с незаметным переключением, когда канал исчерпал квоту, упёрся в лимит, потерял ключ или упал на стороне провайдера.**

`dsh_multi_api` переносит слой «каналы + сопоставление моделей + отказоустойчивость» из new-api внутрь процесса DSH. Плагин регистрируется как обычный `LlmAdapter` за виртуальным провайдером `relay`. Настроенные модели появляются в выборе модели в чате и ведут себя как штатные.

- **Многоканальная маршрутизация** — логическую модель можно привязать к любому числу каналов; сортировка по приоритету, внутри приоритета — по весу, при сбое берётся следующий кандидат.
- **Автоматическое переключение** — исчерпанная квота, неверные учётные данные, лимиты, `5xx`, таймауты и «у эндпоинта нет такой модели» вызывают переход. Если видимый вывод уже пошёл, переключения нет — две разные генерации не склеиваются.
- **Остывание с восстановлением** — 30 минут при исчерпанной квоте, 12 часов при неверном ключе, `Retry-After` при лимитах, экспоненциальная задержка при повторных сбоях; состояние переживает перезапуск и снимается вручную.
- **Визуальное управление** — добавление и правка каналов, привязка моделей, проверка связи, загрузка списка моделей провайдера, просмотр того, какой канал обслужил вызов и сколько было переключений.
- **Ключи не утекают** — лежат в слое учётных данных DSH, не попадают в конфиги, журналы и тексты ошибок.

## Установка / обновление

Нужен DeepSeek Harness `0.2.0-rc.2` или новее (десктоп или веб).

### Из DeepSeek Harness

В левой панели **Plugins → Add plugin**: выберите каталог этого репозитория или вставьте Git-адрес в поле поиска.

### Через CLI `dsh`

```sh
dsh plugin --profile desktop add git+https://github.com/XiaoCai-dev/dsh_multi_api.git
```

Из локального каталога (для разработки):

```sh
dsh plugin --profile desktop add /path/to/dsh_multi_api
```

Обновление:

```sh
dsh plugin --profile desktop add git+https://github.com/XiaoCai-dev/dsh_multi_api.git
```

Удаление:

```sh
dsh plugin --profile desktop remove dsh_multi_api
```

После установки перезапустите DSH — в левой панели появится **Channel relay**.

## Использование

| Раздел | Что делает |
| --- | --- |
| **Каналы** | Добавление, правка, удаление каналов: Base URL, API-ключ, приоритет, вес, таймаут и список моделей канала (`логическая` или `логическая=у_провайдера`). Действия в строке: проверка связи, загрузка моделей провайдера, снятие остывания. |
| **Маршруты моделей** | По карточке на каждую логическую модель: цепочка переключения (канал A → канал B) и реальный id модели за каждым каналом; здесь же добавляются и удаляются привязки. |
| **Вызовы и переключения** | Последние 200 вызовов: результат (успех / переключение / все каналы отказали), модель, общая длительность, цепочка каналов; разверните строку, чтобы увидеть код ошибки и время каждой попытки. |
| **Выбор модели** | Настроенные логические модели видны в группе `Channel relay`; выбрали — работаете. У моделей с несколькими каналами есть значок `×N`. |

### Быстрый старт

1. **Каналы → Добавить канал**: Base URL пишите до `/v1` (например `https://api.deepseek.com/v1`), укажите API-ключ и перечислите модели канала.
2. Чтобы проверить переключение, **добавьте второй канал** с тем же именем модели и большим числом приоритета (больше = резерв).
3. В чате нажмите на имя модели над полем ввода → **Модель** → выберите её в группе `Channel relay`.

С одним каналом плагин ничего не меняет и никогда не переключается — для отказоустойчивости нужно минимум два канала с одной логической моделью.

В журнале сессии всегда записан `provider: relay`, поэтому там не видно, какой канал ответил; переключения живут только в журнале плагина.

### Настройка канала

![Форма добавления канала](docs/setup-channel.png)

Base URL — до `/v1`. Поле моделей принимает `логическая` или `логическая=у_провайдера`; при сохранении привязки этого канала заменяются, и результат сразу виден в выборе модели.

### Использование в чате

![Группа Channel relay в выборе модели](docs/model-picker.png)

Выбираете — и работает как любая штатная модель. Если логическая модель опирается на несколько каналов, у пункта есть значок `×N`: это размер пула переключения.

## Правила переключения

| Сигнал провайдера | Код отказа | Переключение | Состояние канала |
| --- | --- | --- | --- |
| 402 / 403 / 429 с текстом про квоту (`quota`, `balance`, `insufficient`) | `QUOTA` | да | остывание 30 минут |
| 429 лимит запросов (с `Retry-After`) | `RATE_LIMIT` | да | остывание (по заголовку, 45 с по умолчанию) |
| 401 / 403 неверный ключ | `INVALID_CREDENTIAL` | да | недействителен 12 часов, без авто-восстановления |
| 404 или «модель не существует» | `MODEL_UNSUPPORTED` | да | эта привязка остывает 5 минут |
| 5xx | `SERVER` | да | считается; остывание после серии отказов |
| Сбой соединения / таймаут | `TRANSPORT` / `TIMEOUT` | да | экспоненциальная задержка, максимум 10 мин |
| 200 с пустым потоком | `EMPTY_RESPONSE` | да (один раз) | без остывания |
| 400 неверный запрос, слишком длинный контекст | `INVALID_REQUEST` / `CONTEXT_WINDOW_EXCEEDED` | нет | без остывания |
| Отмена пользователем | `aborted` | нет | без остывания |

Остывающий канал не исчезает из кандидатов, а уходит в конец. Если остывают все, хотя бы один всё равно будет опрошен.

Когда у логической модели несколько каналов, наружу отдаются **самые осторожные** характеристики: окно контекста — минимум по каналам, иначе план, рассчитанный на самый широкий канал, случайно упрётся в более узкий резерв.

## Разделение с `dsh-llm-retry`

- **Этот плагин**: переключает каналы — один запрос проходит по списку каналов.
- **`dsh-llm-retry`**: повторяет кратковременные сбои на том же канале и перезапускает шаг.

Поэтому маршрут возвращает `undefined` из `providerRetryPolicy()`: хост не должен повторять запрос, который уже перебрал все каналы.

## Данные и приватность

| Что | Где |
| --- | --- |
| Каналы, привязки моделей, состояние остывания, журнал вызовов | `$DSH_HOME/storages/channel_relay/` |
| API-ключ | `$DSH_HOME/.credentials.yaml`, запись `dsh-channel-relay/<channel-id>` |

Удаление канала убирает и его привязки, состояние остывания и ключ. Журнал хранит последние 200 записей. Тексты ошибок и журналы вычищаются: ключи и тела запросов к провайдеру не показываются.

## Известные ограничения

- **Только текст**: возможности изображений не заявлены, запросы с картинками идут по деградированному пути DSH.
- **Только OpenAI-совместимый протокол** (`/chat/completions`): Anthropic Messages и OpenAI Responses не реализованы.
- **Нет общего состояния между процессами**: остывание живёт в процессе; два экземпляра DSH считают раздельно.
- **Переключения невидимы в журнале сессии**: так задумано; диагностируйте по журналу плагина.
- При смене канала теряются подпись reasoning и кеш промпта провайдера — принятая плата.

## Разработка

```sh
node --check index.js    # Host-половина
node --check client.js   # Client-половина
```

- `index.js` — регистрация `LlmAdapter`, маршрутизация, перевод SSE → `StreamChunk`, автомат остывания, домен хранилища и учётные данные, 9 RPC-маршрутов
- `client.js` — иконка в боковой панели и основная панель, общение с хостом через `/api/dsh_multi_api/*`
- `DESIGN.md` — обоснование решений и компромиссы (включая аудит возможностей DSH)
